Fundamentos

Introducción a los sistemas operativos

Un sistema operativo permite ejecutar programas y administrar el hardware sin que cada usuario tenga que controlar la CPU, la memoria o el disco por su cuenta. Este tema explica para qué sirve, cómo se relaciona con las aplicaciones y de qué manera reparte los recursos cuando varias tareas ocurren al mismo tiempo.

Concepto y propósito del sistema operativo

Un sistema operativo es el software que permite ejecutar otros programas y administrar los recursos físicos del computador: la memoria, los periféricos, el almacenamiento y la CPU. Lo hace de manera eficiente, ordenada y segura, y al mismo tiempo ofrece interfaces para que usar el equipo no dependa de conocer cada componente por dentro.

La forma principal de lograrlo es la virtualización. El sistema operativo toma un recurso físico, como el procesador, la memoria o el disco, y lo presenta como una versión más general y fácil de usar. Por eso a veces se describe como una máquina virtual: no reemplaza al hardware, lo organiza para que varios programas puedan compartirlo (Arpaci-Dusseau y Arpaci-Dusseau, 2023).

Qué pasaría sin un sistema operativo

Sin ese intermediario, el usuario tendría que hablar directamente con el hardware. El problema no es solo de comodidad. Hace falta saber qué hace cada componente, cuáles son sus límites y cómo configurarlo sin dañarlo. Además, el sistema operativo existe para cumplir tres objetivos que un usuario no podría sostener a mano en el día a día (Wolf et al., 2015):

  • Abstracción. Oculta el detalle del hardware. Guardar un documento se parece a elegir una carpeta, no a decidir en qué bloque del disco va cada byte.
  • Administración de recursos. Reparte memoria, almacenamiento y tiempo de procesador para que cada programa reciba lo que necesita.
  • Aislamiento. Permite que varias personas y varios programas usen el mismo equipo sin pisarse los datos ni los recursos.

En la práctica, eso se nota en tareas que hoy parecen simples. Sin sistema operativo habría que asignar a mano el espacio para crear o abrir un archivo, vigilar que un solo programa no consuma toda la CPU y la memoria, y controlar lo que hace cada persona si el computador lo comparten compañeros o familiares. El resultado no sería ni cómodo ni eficaz. Por eso el sistema operativo quedó como la base para el trabajo, el estudio y el uso cotidiano.

Idea clave: el hardware aporta la capacidad física; el sistema operativo la vuelve utilizable, la reparte y evita que un programa o un usuario la acapare.

Relación entre hardware, software, usuario y aplicaciones

Estos cuatro elementos no trabajan por separado. Forman un flujo de instrucciones: el usuario pide algo, la aplicación traduce esa petición, el sistema operativo prepara los recursos y el hardware ejecuta el trabajo físico.

Cada elemento

El hardware son los componentes físicos que aportan los recursos: CPU, RAM, almacenamiento, GPU y dispositivos de entrada y salida. Son los únicos que ejecutan instrucciones de verdad. Por sí solos solo repiten un ciclo —leer una instrucción, avanzar y ejecutar— hasta que alguien carga un programa.

El software son los programas que se guardan en el computador y usan esos recursos para funcionar. Dentro de este grupo están el sistema operativo y las aplicaciones.

El sistema operativo gestiona el hardware y sirve de intermediario. Virtualiza los recursos para que las aplicaciones los usen sin competir de forma desordenada. El usuario también puede hablarle directamente mediante el intérprete de comandos, o shell.

Las aplicaciones son los programas con los que la persona trabaja todo el tiempo: el navegador, el editor de texto, el reproductor de música. Suelen escribirse en lenguajes de alto nivel, como Python, Java o C#, y por eso pueden llevarse a distintos sistemas. Aun así dependen de un compilador o un intérprete, y del sistema operativo, para que esas instrucciones lleguen al hardware.

El usuario, para el sistema, no es “la persona” en abstracto. También se virtualiza: una cuenta, con un identificador y unos permisos, que el sistema revisa antes de dejar ejecutar una acción.

Cómo se apilan

Carretero et al. (2001) ordenan esta relación en capas. Arriba está el usuario. En el medio, el software: las aplicaciones y el sistema operativo, y este último se divide a su vez en shell, servicios y núcleo. Abajo queda el hardware.

Ejemplo: guardar un archivo de Word

El flujo se ve claro al guardar un documento. Participan los cuatro elementos, en este orden:

  1. Usuario. En Word pulsa Ctrl+G o elige Archivo y luego Guardar.
  2. Aplicación. Word convierte esa acción en una petición para almacenar el estado del archivo.
  3. Sistema operativo. Comprueba la ruta y los permisos, y organiza la escritura mediante el sistema de archivos.
  4. Hardware. La CPU y la RAM intervienen en la operación, y el disco duro o el SSD conservan la información.

Funciones principales del sistema operativo

Carretero et al. (2001) agrupan el trabajo del sistema en tres grandes tareas: gestionar los recursos, ofrecer servicios a los programas y ejecutar los mandatos del usuario. De ahí salen funciones que se notan en el uso diario.

Ejecución de programas y gestión de procesos

El sistema reparte el procesador entre los programas que están abiertos. Al virtualizar la CPU, varios programas pueden avanzar aunque el equipo tenga un solo procesador. Al iniciar sesión en Windows, por ejemplo, arrancan varias aplicaciones a la vez: el sistema las va turnando sin que la persona decida el orden de cada instrucción.

Gestión de la memoria

A cada programa le asigna un conjunto de direcciones privadas y las relaciona con la memoria física. Así, tener muchas pestañas en el navegador y, al mismo tiempo, un documento de Office no hace que un programa escriba encima de los datos del otro.

Gestión de dispositivos de entrada y salida

El sistema controla teclado, ratón, impresora, cámara y discos para que ni el usuario ni cada aplicación los configuren a mano. Ese trabajo lo hacen los drivers: código del propio sistema que sabe hablar con un dispositivo concreto (Arpaci-Dusseau y Arpaci-Dusseau, 2023). Al conectar una impresora, el sistema busca ese controlador, en el equipo o en internet, y a partir de ahí puede usarla.

Protección y aislamiento

El sistema evita que una aplicación dañe a las demás o al propio sistema. Para eso separa dos modos de ejecución. En modo usuario, un programa no puede hacer por su cuenta operaciones delicadas, como acceder directo a un disco. Si necesita un servicio, hace una llamada al sistema: una instrucción especial, el trap, pasa el control al sistema y sube el privilegio a modo kernel. Cuando la operación termina, el control vuelve al programa y se restablece el modo usuario.

Por eso, si un programa se cierra por un fallo interno, las demás ventanas siguen abiertas. Y si alguien intenta manipular la unidad de almacenamiento saltándose esas reglas, el sistema puede negar la operación antes de que el componente quede en un estado inconsistente.

Interfaz de usuario

También facilita el diálogo con la persona. El shell permite escribir comandos, y la interfaz gráfica permite abrir un programa con un icono, mover archivos o revisar una carpeta sin memorizar la sintaxis. Un acceso directo y un ping para probar una red son la misma función vista de dos maneras.

Administración de los recursos del sistema

Decir que el sistema operativo administra recursos significa que el procesador, la RAM, el almacenamiento y los dispositivos tienen un límite, y los procesos compiten por ellos. El sistema aplica políticas para repartirlos según lo que el equipo necesita en ese momento. Esa política puede buscar eficiencia, equidad o una mezcla de ambas (Wolf et al., 2015; Arpaci-Dusseau y Arpaci-Dusseau, 2023).

Como gestor, el sistema cumple tres labores: asignar el recurso, protegerlo para que nadie lo use fuera de lo permitido y llevar la cuenta de quién lo está usando (Carretero et al., 2001).

Procesador

El tiempo de CPU se reparte en turnos. Al virtualizar el procesador, cada programa trabaja como si lo tuviera para sí, aunque en realidad lo comparte. Un temporizador interrumpe de forma periódica para que el sistema recupere el control: así no depende de que un programa suelte la CPU por voluntad propia. Luego un planificador elige el siguiente proceso y el cambio se hace con un cambio de contexto. Decidir cuál corre es la política; la forma de cambiar de uno a otro es el mecanismo.

Memoria RAM

Cada proceso recibe un espacio de direcciones privado, asociado a la memoria física. La Unidad de Manejo de Memoria (MMU) es el hardware que impide que un proceso sobrescriba la memoria de otro, incluida la del propio sistema operativo.

Dispositivos

Hay dos formas de compartirlos. Algunos, como la impresora, necesitan acceso exclusivo: si dos trabajos se mezclan, el resultado se corrompe. El sistema forma una cola, el spool, y bloquea el dispositivo para un trabajo a la vez. Otros pueden atender a varios usuarios por un mismo canal, y entonces cada petición espera su turno en una fila.

Almacenamiento

El disco se comparte de otra manera. El sistema no fabrica un disco distinto para cada aplicación: los archivos conviven en el mismo medio y el sistema de archivos decide dónde y cómo se guardan. Si una política pone un límite, el usuario no puede saltárselo solo con pedirlo. Para que ese control sea real hacen falta la MMU y la separación entre modo usuario y modo kernel.

Cuando cuatro tareas quieren la CPU a la vez

Pensemos en un computador con un solo núcleo y un solo hilo. Al mismo tiempo se descarga un archivo, suena música, se abre una página en el navegador y se actualiza una aplicación. Los cuatro procesos pueden necesitar el procesador en el mismo instante: hay datos que guardar, audio que decodificar, un clic que atender y un paquete de actualización que procesar.

Como la CPU es una, cada proceso espera su turno. El sistema reparte intervalos cortos con el temporizador. En cada interrupción guarda el estado del proceso que iba corriendo, elige el siguiente y más adelante retoma el anterior desde donde quedó. La alternancia es tan rápida que la persona percibe que todo ocurre a la vez. Si la descarga está esperando paquetes de la red y no necesita la CPU, ese tiempo se lo ceden a las otras tres.

Si el sistema no pudiera quitarle la CPU a un proceso, cada programa la conservaría hasta que decidiera soltarla. Uno que se quede al 100% y no ceda el turno congelaría la descarga, la música, la actualización y el navegador.

Los procesadores actuales tienen varios núcleos e hilos, así que sí pueden avanzar varias tareas en el mismo instante. Aun así suele haber más procesos que núcleos, y el reparto sigue siendo necesario.

Gestión del procesador y de los procesos

Un programa es un conjunto de instrucciones y datos guardado en el almacenamiento. Un proceso es ese programa en ejecución: una instancia concreta, ya cargada y trabajando (Arpaci-Dusseau y Arpaci-Dusseau, 2023; Wolf et al., 2015).

El proceso se reconoce por su estado de máquina: la memoria que puede direccionar, los registros (incluido el contador de programa y el puntero de pila) y la información de entrada y salida, como los archivos que tiene abiertos. El procesador es la unidad que ejecuta tanto los procesos del usuario como los del sistema. Sobre esa CPU, el sistema se encarga de arrancar el equipo, atender interrupciones y excepciones, y multiplexar el tiempo entre procesos.

Cómo se turnan

El sistema ejecuta un proceso, lo interrumpe con el temporizador —o porque el proceso pasa a bloqueado— y luego corre otro. Da la ilusión de varios procesadores, aunque sea uno solo avanzando en ciclos muy cortos. El costo es que cada proceso tarda un poco más que si estuviera solo; a cambio, las tareas progresan “a la vez”.

En el modelo básico, un proceso está en uno de tres estados. El sistema alterna listo y en ejecución según a quién le toque la CPU. Bloqueado aparece cuando el proceso espera una operación de entrada o salida; al completarse, vuelve a listo.

Para no perder el hilo, el sistema guarda una lista de procesos. Cada entrada tiene el estado, un identificador y el contexto de los registros. Al detener un proceso, copia esos registros; al reanudarlo, los restaura. La política —qué proceso conviene ejecutar— queda separada del mecanismo —cómo se hace el cambio—. Así se puede cambiar la regla de turno sin rehacer el cambio de contexto.

Planificación de la CPU

El planificador elige cuál de los procesos en estado listo usará el procesador. Se apoya en el historial de cuánto ha corrido cada uno, en el tipo de carga y en métricas como el tiempo de retorno (desde que el proceso llega hasta que termina), el tiempo de respuesta (hasta la primera vez que se ejecuta) y la equidad. Equidad y rendimiento suelen tirar para lados distintos: acelerar unos trabajos puede dejar otros esperando.

Hay varias políticas, y ninguna gana en todo:

  • FIFO (primero en llegar, primero en salir) atiende en orden de llegada. Si entra primero un trabajo muy largo, los cortos quedan detrás hasta que ese termine.
  • SJF y STCF prefieren el trabajo más corto, o el que menos tiempo le queda. Mejoran el retorno cuando se conoce la duración, y castigan a los trabajos largos.
  • Round robin da a cada proceso un intervalo corto y luego pasa al siguiente. Responde pronto, aunque el trabajo completo puede tardar más por tantos cambios.

La entrada y la salida también cuentan. Si un proceso está bloqueado esperando un disco o la red, el planificador le cede la CPU a otro que sí esté listo.

Si los procesos no se administran

  • Acaparamiento. Un proceso se queda con la CPU hasta que él decida devolverla, y el equipo puede congelarse.
  • Mala respuesta. Con una cola estricta, un trabajo largo bloquea a los demás. En una terminal pasa algo parecido: hay que esperar a que el comando actual termine para lanzar el siguiente.
  • CPU desaprovechada. Si un proceso bloqueado en una espera no suelta el procesador, ese tiempo no se reutiliza.
  • Falta de equidad. Algunos procesos listos tardarían demasiado o no llegarían a ejecutarse.

Administración de la memoria

La RAM (Random Access Memory, memoria de acceso aleatorio) es la memoria principal. Ahí se cargan, de forma temporal, las instrucciones y los datos de lectura y escritura de los programas que están en marcha. El procesador toma de esa memoria lo que va a ejecutar. Gracias a ella, cambiar de un programa a otro es rápido: el sistema no tiene que ir al disco en cada alternancia.

Mediante la virtualización, cada proceso recibe un espacio propio con tres zonas. El código son las instrucciones. La pila (stack) sigue la cadena de llamadas, las variables locales y los parámetros. El heap guarda la memoria que el programa pide de forma dinámica mientras corre. Entre el heap y la pila queda un hueco, porque ambas zonas crecen o se reducen con el tiempo.

Ese espacio se numera con direcciones virtuales, de 32 o 64 bits según el sistema. Si el proceso A pide su dirección 0, el hardware y el sistema la traducen a otra dirección física, por ejemplo 320 KB. El programa no tiene que enterarse. La virtualización de la memoria persigue tres metas: transparencia, para que el programa crea que usa la memoria física; eficiencia, para que la traducción sea rápida y no gaste demasiada memoria en las propias tablas (aquí ayuda el TLB, una caché de traducciones dentro de la MMU); y protección, para que un proceso no lea ni escriba la memoria de otro ni la del sistema operativo.

RAM y almacenamiento permanente

Las dos guardan datos, y aun así cumplen papeles distintos. La RAM sostiene lo que está en ejecución. El HDD o el SSD conservan el sistema, las aplicaciones y los archivos aunque se corte la energía. De ahí el sistema los carga hacia la RAM cuando hacen falta.

Comparación entre la memoria RAM y el almacenamiento permanente.
Aspecto Memoria RAM HDD o SSD
Función Guarda programas en ejecución y sus datos de trabajo. Conserva de forma permanente programas y archivos. El sistema los carga a la RAM para usarlos.
Volatilidad Al apagar o cortar la energía, pierde su contenido. Mantiene los datos sin energía.
Velocidad y capacidad Es más rápida y, en comparación, tiene menos espacio. Es más lenta y ofrece mucha más capacidad. Ejecutar todo desde el disco haría el equipo demasiado lento.
Quién la organiza El gestor de memoria, con la MMU y los espacios de direcciones. El sistema de archivos.

Gestión de dispositivos de entrada y salida

Los periféricos no se conectan todos igual de cerca del procesador. Un bus más rápido suele ser un camino más corto y más costoso, así que la memoria vive junto a la CPU y dispositivos como el teclado, el ratón o un disco USB quedan más afuera. En un equipo actual, la gráfica suele hablar con el procesador al nivel de la memoria, mientras la red, los USB y muchos discos pasan por un chip dedicado a la entrada y la salida.

El sistema no adivina el estado de un dispositivo: lo lee y lo escribe en registros de estado, de comando y de datos. El protocolo básico es esperar a que el dispositivo esté libre, enviarle los datos y escribir el comando. Si el sistema se queda preguntando una y otra vez si ya terminó —eso es el polling—, desperdicia CPU. Por eso, con dispositivos lentos, deja el proceso dormido y atiende otro; cuando el dispositivo acaba, manda una interrupción y una rutina del sistema despierta al proceso. En dispositivos muy rápidos, el polling a veces conviene más que la interrupción, porque avisar tantas veces también tiene un costo.

Otro cuello de botella es la E/S programada: la CPU copia ella misma cada dato entre la memoria y el periférico. Para un bloque grande, eso ocupa al procesador en un traslado mecánico. El DMA (acceso directo a memoria) es un componente que hace esa copia y, al terminar, avisa con una interrupción. Las instrucciones que mueven estos dispositivos son privilegiadas. Si cualquier programa pudiera leer o escribir el disco por su cuenta, no habría control posible sobre los datos.

Para qué sirve un driver

El sistema se mantiene neutro respecto al aparato concreto. Un sistema de archivos tiene que funcionar igual si el disco es SATA, USB o NVMe. El driver es el trozo de software que sí conoce ese aparato y encapsula el detalle. En Linux, el camino simplificado va de la aplicación a la API, de ahí al sistema de archivos, luego a una capa genérica de bloques, después al driver y, al final, al hardware, mediante registros e interrupciones.

Cuando un driver falla o no corresponde al equipo, las consecuencias se notan enseguida:

  • Fallos del núcleo. Los drivers son una parte enorme del código del sistema —en Linux se ha estimado cerca del 70%— y muchos los escriben quienes fabrican el dispositivo, no un equipo dedicado al kernel. Por eso son una fuente frecuente de cuelgues.
  • Errores poco claros. Al encapsular el dispositivo se pueden perder detalles. Un disco SCSI en Linux informa mejor un fallo; otros dispositivos devuelven un error genérico y cuesta saber qué pasó.
  • Incompatibilidad. Un driver se escribe para un núcleo concreto. El de Windows no sirve en Linux, y al revés. Si el driver coincide con el sistema pero no con el hardware, el sistema puede instalarlo y, aun así, no usarlo, porque no hay un dispositivo que responda a esas órdenes.

Administración de archivos y directorios

Un archivo es la unidad lógica del almacenamiento permanente. Agrupa información relacionada bajo un nombre, y es la forma que tiene el usuario de manejar ese almacenamiento. Por dentro es una secuencia de bytes. El sistema, en general, no decide si esos bytes son una foto, un video o código: los guarda y los devuelve tal cual. En UNIX, además del nombre visible, el archivo tiene un identificador numérico interno, el i-number.

Un directorio, o carpeta, relaciona el nombre que ve la persona con ese identificador. En UNIX, un directorio guarda pares de nombre e i-number. Como un directorio puede contener otros, se forma un árbol desde una raíz. Cada carpeta incluye dos entradas especiales: . apunta a sí misma y .. apunta a la carpeta padre.

Qué hace el sistema con ellos

Un proceso solo llega a un archivo por la interfaz del sistema operativo. Las operaciones de todos los días pasan por ahí:

  • Crear y abrir. El sistema comprueba que el archivo exista o pueda crearse, que los permisos alcancen y que el medio lo permita. Luego entrega un descriptor. En UNIX, abrir o crear se pide con open, y la bandera O_CREAT indica que hay que crearlo si no está.
  • Leer y modificar. El sistema mantiene un apuntador a la última posición, que avanza con cada lectura o escritura y también puede recolocarse. Al cerrar, vuelca a disco lo que todavía estaba en buffers de la RAM. Renombrar se pide con rename.
  • Eliminar. En UNIX, unlink quita un nombre del directorio. El archivo desaparece del todo cuando ya no queda ningún nombre apuntándolo.
  • Organizar carpetas. mkdir crea un directorio, opendir y readdir leen su contenido, y rmdir lo borra solo si está vacío.
  • Concurrencia. El sistema lleva tablas de archivos abiertos y puede negar un segundo acceso aunque los permisos existan. Así dos procesos no escriben el mismo archivo a la vez y dejan los datos a medias.

Permisos

CPU y RAM se reparten en espacios bastante privados. El disco, en cambio, lo comparten usuarios y procesos, así que hace falta decir quién puede leer, escribir o ejecutar. Tres modelos cubren la mayoría de los casos:

  • FAT usa atributos simples: oculto, solo lectura, sistema o archivado. Nació para equipos de un solo usuario.
  • UNIX usa nueve bits en tres grupos —dueño, grupo y otros—, cada uno con lectura, escritura y ejecución. En una carpeta, escribir permite crear o borrar entradas, leer permite listarlas y ejecutar permite entrar. Con chmod 600 un archivo queda solo para su dueño, con lectura y escritura.
  • Las listas de control de acceso (ACL) guardan, en cada archivo, permisos por usuario o por grupo. Así no hace falta que el archivo pertenezca a un único grupo. Las versiones de Windows con núcleo NT las incorporan.

Sistemas de archivos

Un sistema de archivos es el esquema con el que se organiza un volumen. Si el sistema operativo no lo reconoce, no puede mostrar el contenido y, en un mal caso, puede dañarlo. Al crear una partición queda una unidad con su propia descripción: estructura, descriptores, bloques libres y bloques de datos.

De cada archivo se guardan metadatos —dueño, permisos, fechas, tamaño y ubicación—, normalmente asociados al i-number. El directorio solo guarda el nombre y ese número. En conjunto, el sistema de archivos convierte bloques sueltos en archivos y carpetas comprensibles, permite elegir un formato según el uso (rendimiento, intercambio entre equipos o límites del hardware) y, con el montaje, deja convivir varios formatos en un mismo árbol.

Núcleo, controladores y llamadas al sistema

Núcleo o kernel

Es la capa del sistema operativo más cercana al hardware. Gestiona los recursos y concentra la funcionalidad básica, por eso se ejecuta en modo kernel. El resto de capas puede trabajar con menos privilegios. En un núcleo monolítico, esas rutinas viven en un único componente privilegiado. En un micronúcleo, el núcleo se reduce al mínimo y deja el manejo de muchos servicios en procesos sin privilegio.

Controlador y driver

En el habla cotidiana, controlador y driver se usan como sinónimos. Conviene separarlos, como hacen Carretero et al. (2001). El controlador es hardware: una unidad que maneja uno o varios dispositivos del mismo tipo, intercambia datos con la memoria, compensa la diferencia de velocidad y detecta errores. El driver, o manejador, es software del sistema operativo. Recibe una petición abstracta, la traduce a lo que el controlador entiende y envía las órdenes en el orden correcto.

Llamada al sistema

Un proceso sin privilegios no llega directo a los dispositivos. Cuando necesita una acción privilegiada, la pide con una llamada al sistema. Las librerías y los lenguajes envuelven esas llamadas en APIs, para que quien programa no tenga que armar la instrucción de bajo nivel a mano.

Leer un archivo, paso a paso

Si una aplicación abre notas.txt desde un disco, los tres componentes se encadenan así:

  1. La aplicación pide abrir notas.txt. El sistema comprueba que el archivo exista y que la cuenta tenga permiso.
  2. El núcleo devuelve un descriptor: un entero con el que la aplicación se referirá a ese archivo abierto.
  3. Con el descriptor, la aplicación llama a read. El control pasa al núcleo.
  4. El sistema de archivos calcula qué bloques hay que leer, según la posición y el tamaño pedidos, y se los solicita al manejador del disco. A veces lee un bloque entero aunque solo haga falta un fragmento.
  5. El manejador traduce la petición y se la entrega al controlador. Con un disco, el proceso suele bloquearse a la espera de una interrupción.
  6. El controlador termina la lectura y avisa con una interrupción. El manejador revisa si hubo errores y devuelve el estado al sistema de archivos.
  7. Los datos quedan en el buffer de la aplicación y read informa cuántos bytes leyó.

Intérprete de comandos y consola

Consola o terminal

La terminal de texto es el medio por el que el computador recibe y envía una secuencia de caracteres. Hoy se usan emuladores: toman lo que se teclea, se lo entregan al sistema y muestran la respuesta, imitando a las terminales físicas de antes.

Shell

El intérprete de comandos, o shell, es el módulo que permite dialogar con el sistema de forma interactiva. Funciona como un bucle: espera una orden, la analiza, la ejecuta con los servicios del sistema y vuelve a esperar. En modo texto, al terminar muestra un indicador, el prompt, para avisar que ya puede recibir otra línea. Algunas órdenes las resuelve el propio intérprete, sin llegar a crear un proceso nuevo.

Aprendizaje Hay que recordar la sintaxis, y cambia de un sistema a otro. Muestra las acciones y se explora de forma más directa.

Borrar un archivo ilustra las dos vías: en la terminal, del en Windows o rm en UNIX; en la gráfica, el icono de la papelera o la tecla Supr sobre el archivo seleccionado.

Cinco comandos de Windows

Estos mandatos salen de la consola de Windows (cmd). La sintaxis completa está en la documentación de Microsoft; aquí queda la forma de uso y un ejemplo concreto.

dir

cmd.exe — dir 
C:\> dir /a

dir [<unidad>:][<ruta>][<archivo>]

Muestra los archivos y subdirectorios de una carpeta. Sin parámetros, lista el directorio actual, con fecha, hora, tamaño y espacio libre.

Ejemplo: dir /a incluye también los archivos ocultos.

cd

cmd.exe — cd 
C:\> cd C:\Users\Jeronimo\Documents

cd [/d] [<unidad>:][<ruta>]

Muestra o cambia el directorio actual. Sin parámetros, solo indica en qué unidad y carpeta está la terminal. cd .. sube a la carpeta padre.

Ejemplo: cd C:\Users\Jeronimo\Documents

mkdir

cmd.exe — mkdir 
C:\> mkdir C:\Users\Jeronimo\Documents\Sistemas_Operativos

mkdir [<unidad>:]<ruta>

Crea un directorio. Si el nombre lleva espacios, hay que ponerlo entre comillas: sin ellas, la consola interpreta cada palabra como una carpeta distinta.

Ejemplo: mkdir C:\Users\Jeronimo\Documents\Sistemas_Operativos

copy

cmd.exe — copy 
C:\> copy notas.txt C:\Users\Jeronimo\Documents\Sistemas_Operativos

copy <origen> <destino>

Copia uno o varios archivos de una ubicación a otra. Si el origen no está en la carpeta actual, hay que indicar la ruta.

Ejemplo: copy notas.txt C:\Users\Jeronimo\Documents\Sistemas_Operativos

del

cmd.exe — del 
C:\> del notas.txt

del [/p] [/f] [/s] [/q] <nombres>

Elimina uno o varios archivos. Lo borrado por esta vía no pasa por la papelera. Conviene listar antes con dir para confirmar el nombre. Una carpeta no se borra con del: si está vacía, se usa rmdir.

Ejemplo: del notas.txt
